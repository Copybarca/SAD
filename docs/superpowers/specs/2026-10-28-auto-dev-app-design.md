# Auto Dev App — дизайн приложения

## Назначение

`auto_dev_app` — локальный HTTP-сервис для программных агентов. Он хранит постановки задач, краткий журнал выполненных действий, итоговый результат, перечень затронутых Java-классов и элементы scrum-доски. Главный критерий — предсказуемый CRUD API, через который агент может восстановить контекст задачи и записать итог работы без пользовательского интерфейса.

## Цели

- Spring Boot backend на Java 21 без Spring Security.
- REST API с версией `/api/v1` для записи и чтения всех требуемых данных.
- PostgreSQL 16; приложение проверяет наличие целевой БД и создаёт её административным подключением, если БД отсутствует.
- Liquibase является единственным владельцем структуры БД; Hibernate/JPA отображает сущности и проверяет схему через `ddl-auto=validate`.
- Конфигурация задаётся в `application.properties`, значения могут переопределяться переменными окружения стандартным механизмом Spring Boot.
- Локальный запуск приложения и PostgreSQL одной командой `docker compose up -d`.
- Независимые CI-заготовки в `ci/`, без подключения к реальному pipeline и без выполнения deploy по умолчанию.
- Краткие русские Javadoc-комментарии над классами; комментарии над методами не добавляются.

## Не входит в первую версию

- frontend и серверный HTML;
- аутентификация, авторизация и Spring Security;
- подключённый `.gitlab-ci.yml`, публикация в registry или фактический deploy;
- Kubernetes, Swarm, Flux, Telegram, SonarQube, SAST и уведомления;
- поиск, полнотекстовая индексация, пагинация и сложная аналитика;
- изменение сторонних репозиториев.

## Ограничения и принятые решения

- Проект создаётся в `/home/proger/Рабочий стол/auto_dev_app` как отдельный Git-репозиторий без commit/push.
- Используются Maven Wrapper, Spring Boot 4.1.2 (текущая стабильная версия Spring Initializr), Java 21, PostgreSQL driver, Spring Web MVC, Spring Data JPA, Validation, Liquibase и Actuator.
- API возвращает JSON. Ошибки имеют единый объект: `timestamp`, `status`, `error`, `message`, `path`, `fieldErrors`.
- Идентификаторы — `BIGINT GENERATED BY DEFAULT AS IDENTITY`, время — UTC `TIMESTAMP WITH TIME ZONE`.
- Удаление задач физическое. Зависимые журналы действий и затронутые классы удаляются каскадно.
- Входные DTO валидируются: обязательные строки не могут быть пустыми; длины ограничиваются миграцией и Bean Validation.
- Во избежание циклов JPA-сущности не выдаются напрямую из контроллеров: transport DTO находятся в `controller/dto`, mapping — в `view`.

## Рассмотренные подходы

### CI

1. **Выбран:** переносимые POSIX-скрипты в `ci/`, каждый отвечает за один этап, общий `ci/pipeline.sh` вызывает их последовательно. Скрипты можно запускать локально и позднее подключить к GitLab CI без переписывания логики.
2. Скрипты плюс готовый `.gitlab-ci.yml`. Отклонён: параметры registry, runner и окружений пока неизвестны.
3. Дословное копирование готовых GitLab YAML-шаблонов. Отклонено: ненужная привязка к конкретным registry, Kubernetes/Flux и внутренним переменным.

### Схема БД

1. **Выбран:** приложение создаёт только саму PostgreSQL database через административное JDBC-подключение; Liquibase создаёт и изменяет таблицы, Hibernate валидирует соответствие сущностей.
2. Hibernate `ddl-auto=create/update`. Отклонён: конкурирует с Liquibase и не даёт воспроизводимой истории миграций.
3. Создание БД только средствами Docker Compose. Отклонён: не выполняет требование самостоятельного старта приложения вне Compose.

## Архитектура MVC

Корневой пакет: `ru.autodevapp`.

- `model/entity` — JPA-сущности и enum состояния задачи.
- `model/repository` — отдельные Spring Data repository для каждой сущности.
- `model/service` — отдельный use-case service для каждого контроллера; транзакции и правила изменения связей.
- `model/database` — ранний bootstrap существования целевой PostgreSQL database.
- `controller` — тонкие REST-контроллеры, валидация входа и выбор HTTP-статуса.
- `controller/dto` — request/response DTO.
- `view` — mapper-классы, преобразующие сущности в API-представления; frontend пока отсутствует.
- `exception` — предметные исключения и единый обработчик REST-ошибок.

Контроллеры не содержат бизнес-правил или persistence-логики. Каждый новый контроллер использует собственный service; каждый service — соответствующий repository. Модель не зависит от HTTP и DTO.

## Модель данных

### `development_task`

- `id BIGINT` — первичный ключ;
- `title VARCHAR(255) NOT NULL` — заголовок;
- `specification TEXT NOT NULL` — техническое задание;
- `module VARCHAR(255) NOT NULL` — сервис или модуль изменения;
- `result_description TEXT NULL` — итоговый результат;
- `status VARCHAR(32) NOT NULL` — `PLANNED`, `IN_PROGRESS`, `COMPLETED`, `FAILED`;
- `created_at TIMESTAMPTZ NOT NULL`;
- `updated_at TIMESTAMPTZ NOT NULL`.

### `affected_class`

- `id BIGINT` — первичный ключ;
- `task_id BIGINT NOT NULL` — внешний ключ на `development_task`, `ON DELETE CASCADE`;
- `class_name VARCHAR(500) NOT NULL` — полное или краткое имя класса;
- `change_description TEXT NOT NULL` — описание изменения;
- `created_at TIMESTAMPTZ NOT NULL`.

Ограничение уникальности `(task_id, class_name)` не позволяет дважды записать один класс для одной задачи.

### `task_action`

- `id BIGINT` — первичный ключ;
- `task_id BIGINT NOT NULL` — внешний ключ на `development_task`, `ON DELETE CASCADE`;
- `action_description TEXT NOT NULL` — кратко выполненное действие;
- `action_result TEXT NULL` — результат или наблюдение;
- `created_at TIMESTAMPTZ NOT NULL`.

Индекс `(task_id, created_at, id)` обеспечивает стабильное чтение истории по времени.

### `scrum_board_item`

- `id BIGINT` — первичный ключ;
- `title VARCHAR(255) NOT NULL` — заголовок задачи;
- `description TEXT NOT NULL` — описание;
- `module VARCHAR(255) NOT NULL` — сервис или модуль;
- `created_at TIMESTAMPTZ NOT NULL`;
- `updated_at TIMESTAMPTZ NOT NULL`.

В scrum-таблицу не добавляется статус: пользователь запросил только заголовок, описание и модуль. Технические `id` и timestamps нужны API и аудиту изменений.

## REST API

Все коллекции возвращаются в стабильном порядке: новые записи первыми, а история действий — от старых к новым.

### Задачи

- `POST /api/v1/tasks` — создать задачу; `201 Created`.
- `GET /api/v1/tasks` — получить список задач; опциональные фильтры `module` и `status`.
- `GET /api/v1/tasks/{taskId}` — получить задачу вместе с затронутыми классами и журналом действий.
- `PUT /api/v1/tasks/{taskId}` — полностью изменить основные поля задачи.
- `PATCH /api/v1/tasks/{taskId}/result` — записать итог и состояние выполнения.
- `DELETE /api/v1/tasks/{taskId}` — удалить задачу; `204 No Content`.

### Затронутые классы

- `POST /api/v1/tasks/{taskId}/affected-classes` — добавить класс; `201 Created`.
- `GET /api/v1/tasks/{taskId}/affected-classes` — список классов задачи.
- `PUT /api/v1/tasks/{taskId}/affected-classes/{classId}` — изменить запись.
- `DELETE /api/v1/tasks/{taskId}/affected-classes/{classId}` — удалить запись.

### Журнал действий

- `POST /api/v1/tasks/{taskId}/actions` — добавить запись журнала; `201 Created`.
- `GET /api/v1/tasks/{taskId}/actions` — получить хронологическую историю.
- `GET /api/v1/tasks/{taskId}/history` — агрегированное представление задачи, результата, классов и действий одним запросом для агента.
- `PUT /api/v1/tasks/{taskId}/actions/{actionId}` — исправить запись журнала.
- `DELETE /api/v1/tasks/{taskId}/actions/{actionId}` — удалить запись.

### Scrum-доска

- `POST /api/v1/scrum-items` — создать элемент; `201 Created`.
- `GET /api/v1/scrum-items` — список, опциональный фильтр `module`.
- `GET /api/v1/scrum-items/{itemId}` — получить элемент.
- `PUT /api/v1/scrum-items/{itemId}` — изменить элемент.
- `DELETE /api/v1/scrum-items/{itemId}` — удалить элемент.

### Служебный endpoint

- `GET /actuator/health` — проверка готовности приложения и БД.

## Создание БД и миграции

До создания Spring datasource listener читает свойства `app.database.admin-*` и `app.database.name`, подключается к служебной БД PostgreSQL, параметризованно проверяет `pg_database`, а при отсутствии выполняет `CREATE DATABASE` с безопасно провалидированным и экранированным идентификатором. Ошибка подключения или недостаток прав останавливают запуск с понятным сообщением. Уже существующая БД не изменяется.

После bootstrap стандартный datasource подключается к целевой БД. Liquibase применяет `db/changelog/db.changelog-master.yaml`, начальная changeset создаёт таблицы, внешние ключи, ограничения и индексы. Hibernate работает только с `spring.jpa.hibernate.ddl-auto=validate`.

Для Compose PostgreSQL получает административного пользователя из переменных окружения. В примере используются локальные значения по умолчанию, а README предупреждает заменить их вне локальной машины.

## Docker

- Многоэтапный `Dockerfile`: сборка Maven на образе Java 21, runtime на `eclipse-temurin:21-jre-alpine` либо другом реально доступном Alpine-совместимом Java 21 runtime.
- Контейнер запускается непривилегированным пользователем, содержит только runtime и fat JAR, имеет healthcheck.
- `compose.yaml` содержит `app` и `postgres`, persistent volume, healthcheck БД, `depends_on: condition: service_healthy`, все используемые конфигурационные переменные и проброс HTTP-порта.
- Команда запуска: `docker compose up -d --build`. Swarm не используется.

## CI-заготовки

Каталог `ci/` содержит executable POSIX shell-скрипты с `set -eu`:

- `common.sh` — общая проверка переменных и пути проекта;
- `test.sh` — `./mvnw verify`;
- `build-artifact.sh` — воспроизводимая сборка JAR;
- `version.sh` — читает Maven version и вычисляет версию/образный тег по git tags;
- `auto-tag.sh` — функционально переносит SemVer-правила из `includes/auto-tag-job.yml`, но не пушит без явной переменной `CI_PUSH_TAG=true`;
- `build-image.sh` — собирает Docker image только при заданном `DOCKER_IMAGE_REPO`;
- `push-image.sh` — логин и push только при явно заданных registry-переменных;
- `deploy.sh` — безопасная заготовка: печатает план и выполняет внешний `DEPLOY_COMMAND` только при `CI_EXECUTE_DEPLOY=true`; к Compose не подключается;
- `pipeline.sh` — единая точка входа, вызывает test, artifact, version, optional tag, image, push и deploy согласно opt-in переменным;
- `README.md` — контракты переменных и примеры будущего подключения в GitLab CI.

Скрипты не содержат секретов, внутренних адресов, Telegram, SonarQube, SAST, Kubernetes/Flux или runner tags. По умолчанию общий скрипт только тестирует и собирает JAR; сетевые и deploy-действия требуют явного opt-in.

## Проверка

- Unit-тесты сервисов и mapper-классов.
- `@WebMvcTest` для HTTP-контрактов, валидации, кодов ответа и ошибок.
- Repository/Liquibase integration tests через Testcontainers PostgreSQL 16.
- Тест bootstrap создания БД: отсутствие БД, уже существующая БД, неверное имя, недостаток прав.
- Shell syntax check `sh -n ci/*.sh` и изолированные тесты SemVer-вычислений без push.
- Полный `./mvnw verify`.
- `docker compose config` и smoke-test сборки/старта, если Docker доступен; фактический deploy и push не выполняются.

## Критерии готовности

- Чистый checkout собирается Java 21 через Maven Wrapper.
- Все API-маршруты функциональны и документированы примерами `curl` в README.
- Пустой PostgreSQL автоматически получает целевую database и Liquibase-схему.
- Повторный запуск идемпотентен и не пересоздаёт БД или таблицы.
- Проект стартует через Compose и health endpoint становится `UP`.
- CI-скрипты разделены по ответственности, общий скрипт вызывает их, а опасные действия выключены по умолчанию.
- Нет frontend, Security, реального pipeline, push, deploy или commit.
